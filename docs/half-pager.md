# ASTERRA DevOps Project – Half Pager

## מטרת המערכת
המערכת נועדה לקלוט, לעבד ולהציג נתוני שטח (תמונות, מפות, מדידות וכו’) בצורה מאובטחת וקונסיסטנטית.  
הרעיון: יש מקור נתונים מהשטח → הנתונים נשמרים אוטומטית בתשתית → מתבצע עיבוד פנימי → יש תצוגה חיצונית מסודרת שאפשר להראות ללקוח.

המערכת נותנת פתרון end-to-end:
1. איסוף מידע גולמי (Raw Data).
2. טריגר אוטומטי לעיבוד.
3. שמירה מאובטחת של המידע המעובד.
4. ממשק צפייה חיצוני.

---

## ארכיטקטורה (High Level)
המערכת מחולקת במכוון לשני אזורים ברשת:
 הוספתי ציור דיאגרמה כדי להבין בצורה נעימה יותר . - Diagram.png
### 1. אזור ציבורי (Public Zone)
- שרת EC2 ציבורי עם Elastic IP.
- פתוח רק בפורטים 80/443 דרך Security Group ייעודי.
- על השרת רץ `docker-compose` שמרים:
  - WordPress (ממשק להצגת המידע, כתבות, דוחות, מפות).
  - MapServer (שירות GIS שמספק מפות ושכבות מידע גיאוגרפי).
- זה ה-"פנים של המערכת": מה שלקוחות / מנהלים / משתמשים חיצוניים רואים בדפדפן.

מטרה עסקית: לאנושי ניהול/עסקים יש גישה לתוצרים, בלי לתת להם גישה ישירה לתשתית הפנימית ובלי לתת להם SSH.

### 2. אזור פנימי (Private Zone)
- תחנת עבודה פנימית (Internal Workstation EC2) שיושבת ב־Private Subnet בתוך ה-VPC.
- השרת הזה לא נגיש מהאינטרנט, רק ב־SSH מבוקר.
- רץ שם קוד/כלים/סקריפטים שיכולים:
  - למשוך קבצים גולמיים מה-S3.
  - לעבד אותם (ניקוי, המרה, חישובים).
  - לשמור תוצאות מסודרות במסד נתונים.
- מסד נתונים מנוהל (Amazon RDS PostgreSQL) שנמצא גם הוא ברשת הפרטית בלבד, לא חשוף החוצה.
  - ה-DB משמש כ"אמת" של הנתונים אחרי עיבוד (clean data / structured data).
  - כך הנתונים הרגישים לא יושבים על מכונה מזדמנת ואף פעם לא נחשפים החוצה ישירות.

מטרה עסקית: יש לנו סביבת עיבוד מאובטחת שבה נעשה ה-“brain work”, מבודדת מהאינטרנט ומהלקוח.

## נתונים גולמיים ו-Ingestion Pipeline
המערכת כוללת Raw Data Landing Zone:
- S3 Bucket ייעודי (נוצר אוטומטית עם Terraform, בשם ייחודי כמו `<project>-raw-data-<random>`).
- כל קובץ חדש שמועלה לבאקט הזה (למשל צילום שטח / קובץ GIS / Screenshot) מפעיל פונקציית Lambda.

פונקציית Lambda (`ingest-raw-object`):
- רצה אוטומטית על כל העלאה חדשה ל-S3 (Event-driven).
- כותבת לוג ל-CloudWatch עם פרטי הקובץ שהועלה.
- משמשת בתור נקודת כניסה לעיבוד (פה אפשר להוסיף ולשלב לוגיקה: מיקום גיאוגרפי, סוג מדידה, שמירה למטה-דאטה ב-DB וכו’).

מה זה מוכיח:
- ברגע שיש דאטה חדש מהשטח, המערכת מגיבה לבד. אין צורך באדם שירוץ ידנית.
- אפשר להרחיב את ה-Lambda לשלב הבא: נרמול נתונים וטעינה אוטומטית למסד הנתונים (ETL - Extract / Transform / Load).

## ניהול, ניטור, ואבטחה
- כל המשאבים נבנו כ-Infrastructure as Code באמצעות Terraform:
  - VPC, סאבנטים, Security Groups, EC2, RDS, S3, Lambda, IAM Roles, bucket notifications.
  - יש Terraform remote state + DynamoDB lock, כלומר ניהול תשתית אמיתי, לא "לחצתי ידנית בקונסולה".
- CloudWatch משמש לניטור: כל ריצה של הלמבדא מתועדת, אפשר לעקוב אחרי כל קובץ שנכנס למערכת.
- הפרדה רשתית ברורה:
  - שרת ציבורי עם גישה מוגבלת (80/443).
  - תחנת עבודה פנימית שלא חשופה לאינטרנט.
  - RDS שרץ רק בסאבנט הפרטי.
- המשמעות: גם אם מישהו ינסה "להיכנס דרך האתר", הוא לא מגיע למסד הנתונים ולא לאזור העיבוד.

## למה זה חשוב (Value)
1. זה לא סתם EC2 עם אתר. זו פלטפורמה תפעולית:
   - איסוף נתונים → עיבוד פנימי מאובטח → הצגת תוצאה.
2. האוטומציה של ה-ingestion מראה תהליך אמיתי של Data Pipeline (טריגר, לוגיקה, המשך טיפול).
3. יש בידול ברור בין תצוגה עסקית לבין סביבת עיבוד. זה מגן על הדאטה ושומר על שליטה.
4. כל זה נבנה בתצורה שניתנת לשחזור אוטומטי (Terraform) – אין תלות בידיים אנושיות או ב-"מכונה אחת שעובדת במקרה".

במילים פשוטות:
המערכת הזאת היא שלד מבצעי של מוצר GIS/ניתוח שטח בענן – עם public frontend ללקוח, backend פרטי לניתוח, ו-Pipeline אוטומטי של נתונים נכנסים.
